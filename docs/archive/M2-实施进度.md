### 步骤 4：SessionManager 瘦身分析（2026-07-21）

#### 4.1 ✅ 方法映射分析
**文件**：`docs/M2-SessionManager-method-mapping.md`

**分析结果**：
- SessionManager 当前：4057 行，147 个 save/get/clear 方法
- 可委托到 AccountStateModule：~30 个方法（凭据、会话）
- 可委托到 SettingsModule：~40 个方法（用户配置）
- 可委托到 CacheModule：~50 个方法（业务缓存）
- 保留为门面：~27 个方法（向后兼容）
- 保留超星配置：~60 个方法（暂未设计聚合数据类）

**阻塞因素**：
1. **依赖网太深**：SessionManager 被 46 个 Repository 依赖
2. **构造函数修改成本**：直接注入 Module 需要修改所有 Repository 的构造调用
3. **cached* 变量互相依赖**：100+ 个 @Volatile 变量在 init() 中一次性加载，改动风险高

#### 4.2 实施策略调整

**原计划**（10h）：
- 修改 SessionManager 构造函数注入 Module
- 逐个方法委托到 Module
- 删除 cached* 变量和 DataStore key

**问题**：
- 构造函数修改会导致 46 个 Repository 编译失败
- 需要同步修改 AhuPlusApplication 的 46 个 Repository 实例化代码
- 风险高，耗时可能超过 20h

**调整后策略**（分 3 个里程碑）：

**里程碑 A：Module 门面层（3h）**
1. 在 AhuPlusApplication 中创建 5 个 Module 的 Facade 方法
2. Repository 通过 `app.accountState()` / `app.settings()` / `app.cache()` 访问
3. SessionManager 保持不变，作为过渡层继续工作
4. 目标：Repository 适配完成，不再直接依赖 SessionManager 的存储逻辑

**里程碑 B：SessionManager 逐步委托（8h）**
1. SessionManager 内部逐步委托到 Module（保持接口不变）
2. 删除已委托方法的 cached* 变量和 DataStore key
3. 目标：SessionManager 从 4057 行降至 ~1500 行

**里程碑 C：最终清理（2h）**
1. 删除所有已废弃的门面方法
2. SessionManager 只保留必要的兼容层（< 800 行）
3. 全量测试
